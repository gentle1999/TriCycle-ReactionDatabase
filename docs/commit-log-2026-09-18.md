# 提交日志：统一文件导入后端与高吞吐持久化优化

- 日期：2026-09-18
- 提交主题：统一 RustFS 暂存、MolOP 解析和微批数据库持久化链路，并补充生产性能配置指南。

## 背景

此前单文件、本地导入、远程上传和批量上传之间存在不同的领取、解析和写入路径。解析并发受人为 batch 限制，数据库写入又被拆成过多的小会话，导致 CPU 利用率低、解析任务排队以及大批量导入时查询受阻。本次将这些入口收敛到统一的异步导入模型，并将解析吞吐与持久化节奏解耦。

## 主要变更

1. 统一导入流水线：所有文件先写入 RustFS 并登记为 pending，再由共享 dispatcher 连续领取；MolOP 使用按 CPU 配置的共享进程池，持续补充任务，避免每个上传会话单独创建解析进程。
2. 统一持久化：解析结果进入共享的延迟提交器，以微批文件数和帧数共同控制提交；队列凑满或解析池暂时没有待处理任务时执行一次数据库提交，减少并发数据库会话和小事务。
3. 完善失败与重解析语义：保留 source evidence，支持部分成功文件继续写入可用帧；重解析替换旧 parse revision 及其派生帧，避免错误的 single-point 或缺失 segment 证据回退；统一本地导入接口与 worker 入口。
4. 优化数据库写入和项目级状态刷新：集中写入计算、反应、几何和可见性索引，延迟 thermodynamic profile 更新，并通过迁移 `0055_defer_profile_visibility` 将项目级统计刷新安排到批量操作完成后。
5. 增加连续领取、预取、微批持久化和 MolOP 并行度配置；补充多主机部署示例及 RustFS、数据库连接池和线程数的调优说明。
6. 新增中英文性能配置指南，补全自 RustFS 暂存到解析、微批持久化和查询可见性的时序与运维检查项。

## 性能验证

在 24 核部署配置下，使用 256 个真实计算文件进行端到端导入：

- 总数据量：539,273,842 bytes
- 成功：256/256
- worker 首个批次创建到最后一个文件进入终态：85.46 s，约 6.02 MiB/s
- 端到端含队列收尾：约 87.1 s，约 5.90 MiB/s

验证配置包含数据库连接池 `24 + 24`、上传并发 8、worker 并发 16、MolOP `n_jobs=-1`、预取 96、微批 64 文件/2048 帧，并将 OpenMP/BLAS 线程限制为 1，避免进程池内部过度超卖 CPU。
